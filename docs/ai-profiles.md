# AI設定の複数プロファイルと準備済みセッション

`[ai]` を複数持ち、送信ごとに宛先を選び、会議に先立ってAIセッションを起こしておける設計。会議参加モードの契約は [ai-participant.md](ai-participant.md)、定期自動送信は [ai-scheduled.md](ai-scheduled.md) を引き継ぐ。既存docの「複数AIは対象外」はこの文書で改める。

> **利用者が手で起こした既存herdrペインへ接続する案は取り下げた。** 段4の実herdr検証で、接続型ではフック・Codexのサンドボックス許可・Claudeの返送コマンド許可のいずれも渡せず、返し忘れ検知が使えないうえ返送自体が接続先の設定次第になることが確かめられたため。代わりに、KIKIGAKIが従来どおり起動しつつ会議には紐づけない「準備済みセッション」を置く。`attach` / `displayAgent` / 稼働中ペインのその場限りの宛先 / `AIAgentResolver` は実装ごと除く。

## 確定した仕様

タダシとの質問票で決まっており、変えない。

- effortは専用キー `effort`。CLIごとに翻訳する。`extraArgs` との二重指定は拒否する。
- 複数設定は `[[ai]]` の配列。各要素に `name` を持ち、1つ目が既定。既存の単数 `[ai]` は互換で読む。
- 送信ごとに宛先を選ぶ。手動シートと自動送信シートにポップアップを置き、既定は1つ目、会議内では前回の選択を覚える。手動と自動で別のプロファイルを同時に使える。
- herdrセッション・世代・`AIStreamHistory` はプロファイルごとに持つ。会議内の `#n` は全体で通し、印とMarkdownの宛名で区別する。
- AIセッションはKIKIGAKIが `workspace create` と `agent start` で起こす。フック・サンドボックス許可・返送コマンド許可を渡せる形を保つ。
- 会議に紐づかない**準備済みセッション**をいつでも起こせる。録音中でも、その録音とは別に次の会議用を用意できる。録音開始時に、どの準備済みセッションを使うかプロファイルごとに選ぶ。
- プロファイルの `autoStart = true` で、録音開始時に `autoPrompt` と `autoIntervalMinutes` の自動送信を始める。

## 設定

```toml
[[ai]]
name = "議事録"
cli = "codex"
model = "gpt-5.4-codex"
effort = "high"
address = "迅雷へ"
cwd = "~/work/minutes"         # 起動時の作業ディレクトリ。省略時は固定の既定
autoStart = true
autoPrompt = "会議の決定事項と担当・期限をMarkdown議事録へ更新してください"
autoIntervalMinutes = 3

# 配列表記では、この位置の [ai.hotkey] は直前の [[ai]] 要素に属する。
# ホットキーは1つ目のプロファイルにだけ書ける
[ai.hotkey]
modifiers = ["ctrl", "alt", "cmd"]
key = "a"

[[ai]]
name = "相談"
cli = "claude"
effort = "max"
address = "ネオへ"                # cwd を省いたので既定のディレクトリで起動する
```

| キー | 既定と検証 |
| --- | --- |
| name | 省略時は `address` 末尾の「へ」を除いた参加者名。空・改行・NUL・前後空白のみを拒否し、64バイトまで。配列内の重複を拒否する。 |
| effort | 省略時はCLIの既定。単一行でNULを拒否し、CLIごとの値域で検証する。 |
| cwd | 省略時は従来どおり固定の `~/Library/Application Support/KIKIGAKI/ai-work/`。起動時の作業ディレクトリで、プロファイルごとに変えられる。 |
| autoStart | false。trueは配列全体で1つまで。`autoPrompt` が空なら設定エラー。 |
| hotkey | **共通**。1つ目のプロファイルにだけ書ける。2つ目以降にあれば設定エラー。宛先を選び直しても変わらない。 |
| herdrCommand | **共通**。adapterを全チャネルで共有するので、2つ目以降に先頭と違う値を書けば設定エラー。 |
| notifySound | プロファイルごとに効く。返事が届いた枠の設定で鳴らす。 |
| その他 | 既存の `[ai]` と同じ。`cli` `command` `herdrCommand` `model` `address` `extraArgs` `prompt` `notifySound` `allowWork` `autoPrompt` `autoIntervalMinutes` を要素ごとに持つ。 |

単数 `[ai]` と配列 `[[ai]]` の併記は拒否する。TOMLの同名テーブルと配列は文法上も両立しないが、片方だけを黙って採らない。

### effortの翻訳と値域

| CLI | 渡し方 | 値域 |
| --- | --- | --- |
| codex | `-c model_reasoning_effort="<値>"` | none / minimal / low / medium / high / xhigh / max / ultra |
| claude | `--effort <値>` | low / medium / high / xhigh / max |

codexの値域は `codex-rs/protocol/src/openai_models.rs` の `ReasoningEffort` から採る。同リポジトリの `core/config.schema.json` はこのキーを「モデルが提示する非空の文字列」として自由文字列で定義しているため、実際に通る値はモデル依存になる。KIKIGAKIは列挙で先に弾き、CLIが拒否した場合は起動失敗として表示する。claudeの値域は `claude --help` の実測。

codexの `-c` の値はTOMLとして解釈されるので、文字列はクォートを付けて渡す。既存の `notify` と `sandbox_workspace_write.writable_roots` と同じ引数配列の作り方を使い、シェルを経由しない。

`extraArgs` の許可表から `--effort` を外す。旧設定で `extraArgs = ["--effort", "high"]` と書いていた場合は設定エラーにし、`effort` へ移すよう促す。黙って受理すると、翻訳した引数との順序依存で実際の効き方が読めなくなる。

## 送信ごとの宛先選択

手動シートと自動送信シートの先頭にポップアップを置く。既定は配列の1つ目、同じ会議内では前回選んだプロファイルを覚える。手動と自動は別々に覚える。

ポップアップに並ぶのは設定のプロファイルだけである。そのプロファイルに未紐づけの準備済みセッションがあれば、行を「議事録 · Kikigaki 議事録抽出 · 13:05起動」として、どれを使うか選べるようにする。選んだ時点で紐づける。

シートの表題は選択に追随して「議事録へ 自動送信」のように変わる。接続状態・警告・「ペインを開く」も選択中のプロファイルのものを出す。手動シートを開いている間の自動tickスキップは、**同じプロファイルのときだけ**にする。別プロファイルなら手動と自動が同時に走ってよい(確定した仕様)。

印は既存どおり `#3 迅雷へ · 自動` の形で、`participant_name` から宛名を出す。番号は会議内の通し番号のままで、プロファイルごとには振り直さない。会議Markdownの `- 宛先:` も既存の生成をそのまま使う。

**確認質問への返答は、元の質問と同じ宛先へ返す。** 返答シートでは宛先を選ばせず、`prepare` と会話の整合検証でも親子の枠の一致を要求する。別のAIへ返すと、確認した本人ではない相手が答え、しかも元の質問が「返答済み」になってしまう。

各印に出す接続状態と「旧接続からの返事」の判定は、**その質問を送った枠のもの**を見る。選択中の宛先で全行を塗ると、Aを作り直しただけでBの正常な返事まで旧接続扱いになる。

## 準備済みAIセッション

会議の初回送信でセッションを起こすと、ワークスペースの読み込みと議事録の下ごしらえが会議中に走る。それを避けるため、**会議に紐づかないセッションを先に起こしておける**ようにする。起こし方は従来の会議用と同じで、フック・サンドボックス許可・返送コマンド許可はすべて付く。違うのは、どの会議のものでもない状態で待つことだけ。

想定する使い方は連続する会議である。会議1を録音して自動更新を回している最中に、会議2用のセッションを別に起こしておく。会議1が終わり会議2を始めるとき、起こしておいたほうを指定して紐づける。

### 状態

| 状態 | 意味 | 出口 |
| --- | --- | --- |
| 準備中 | `workspace create` と `agent start` の途中。入力可能待ち | 成功で準備済み、失敗で破棄 |
| 準備済み | 起動が終わり、どの会議にも紐づいていない | 紐づけ、破棄、ペイン消失 |
| 紐づけ済み | ある会議のあるプロファイルのチャネルになった | 会議が終わっても紐づいたまま |
| 破棄 | 台帳から外れた | なし |

準備済みのまま待つ時間に上限は置かない。ペインが消えていれば一覧から外す。**録音の停止では破棄しない**。停止後に届く返送の回収は既存の契約どおり続く。

### 台帳

会議の登録簿と同じ `~/Library/Application Support/KIKIGAKI/` に置き、アプリを再起動しても残す。1件が持つのは次のとおり。

- プロファイル名と `slot`、起動に使った設定の固定値
- 起動時刻と、画面に出す表示名
- `AIHerdrConnection`(workspace・pane・CLI種別・session・terminal)とフック用トークン
- 紐づけ先。未紐づけならなし、紐づけ済みなら会議IDとプロファイルの `slot`

紐づけ済みの行を台帳から消さないのは、会議側の `ai/sessions/<slot>/<generation>.json` と同じ接続を指しているためで、正本は会議側に置く。台帳の紐づけ済み行は「この準備済みセッションは使われた」という履歴として残し、一覧には出さない。

台帳が読めないときは準備の操作を無効にし、会議の送信は従来どおり初回起動で続けられるようにする。準備済みが1件も無い状態と、台帳が壊れている状態は区別して表示する。

### 操作

「AIセッションを準備…」は**待機中・録音中・一時停止中のいつでも**使える。シートでプロファイルを選んで起動する。同じプロファイルの未紐づけが既にあっても、もう1つ起こすことを許す。連続する会議のために2つ先まで用意したい場合があるため。

準備の起動中は、その**プロファイルの送信操作と排他**にする。同じプロファイルで会議の初回起動と準備の起動が同時に走ると、どちらの接続を採るかが競合する。別プロファイルの送信は止めない。準備の起動は会議の録音・保存・自動送信を妨げない。

一覧には未紐づけの準備済みだけを出し、プロファイル名・ペインの表題・起動時刻・接続状態を並べる。行ごとに「破棄」と「ペインを開く」を置く。破棄は台帳から外すだけで、ペインのプロセスは終了させない。外部で起きていることの後始末はherdr側で行う。

### ペインの表題を出す

同じプロファイルの準備済みが複数並ぶと、起動時刻だけでは何を下ごしらえさせたのか見分けられない。parliamentのセッションカードと同じ表題を添えて区別する。

値は `herdr pane list` と `agent get` の `terminal_title_stripped` をそのまま使い、無ければ `terminal_title` を使う。実測では `terminal_title` に状態記号が付き(`✳ Kikigaki 議事録抽出`)、`terminal_title_stripped` が素の文字列(`Kikigaki 議事録抽出`)を返す。KIKIGAKIが解釈や整形を足すことはしない。

**台帳には保存せず、一覧を出すたびに引き直す。** 表題はCLIがOSCで設定する値で、利用者やCLIが後から変える。保存すると古い名前が残り続ける。表題はCLIが設定するまで空なので、起動直後など取れない間は「プロファイル名 + 起動時刻」だけに退避する。表題が無いことを異常として扱わない。

表示は名前・表題・時刻の順で「議事録 · Kikigaki 議事録抽出 · 13:05起動」とする。長い表題は末尾を省略し、時刻を押し出さない。一覧・紐づけシート・宛先ポップアップの3か所で同じ形にする。

### 紐づけ

録音開始時、未紐づけの準備済みが1件でもあれば「準備済みのAIセッション」シートを出す。プロファイルごとに次のどちらかを選ぶ。

- 準備済みの「議事録 · Kikigaki 議事録抽出 · 13:05起動」を使う
- 新規に起動する(従来どおり初回送信時に起こす)

未紐づけが1件も無ければシートを出さない。録音そのものはシートの前に始まっており、選択を待つ間も収録は止めない。

送信シートの宛先ポップアップでも、そのプロファイルに未紐づけの準備済みがあれば「議事録 · Kikigaki 議事録抽出 · 13:05起動」として選べる。**選んだ時点で紐づける**。紐づけた後は、そのプロファイルのチャネルとして既存の契約がそのまま適用される。世代は1から始まり、`AIStreamHistory` も受領基準も新しい会議のものになる。

**準備中にAIが読んだ内容をKIKIGAKIは関知しない。** 下ごしらえの結果はAI側の文脈にあるだけで、会議のsnapshotにも受領基準にも入らない。最初の送信は従来どおりその会議のfullから始まる。

### 設定の等価性

紐づけるとき、台帳に固定した起動設定と、会議開始時に固定したそのプロファイルの設定が**同じであることを確かめる**。基準は既存の `prepare` の等価性検証と同じで、`ResolvedAIConfig` 全体の一致を見る。

準備してから設定ファイルを変えた場合、そのセッションは変更前の設定で起きている。CLIもモデルもeffortも作業ディレクトリも違い得るのに、名前が同じというだけで紐づけると、利用者が意図しないAIへ会議の全文が流れる。だから**不一致は候補に出さない**。一覧には残し、「設定が変わったため使えません」と理由を示して、破棄するか設定を戻すかを利用者に選ばせる。黙って消すと、なぜ準備したものが無くなったのか分からない。

枠 `slot` も設定の一部なので、配列の並び順を変えた場合も不一致になる。名前だけを頼りに別の枠へ移し替えることはしない。

### autoStartとの順序

`autoStart` は紐づけの選択が終わってから始める。準備済みを使う選択なら、そのチャネルに紐づけてから最初の期限を数え始める。選択の途中で自動送信を始めると、まだ決まっていない宛先へ最初の1回が飛ぶ。

紐づけシートを出さない場合(未紐づけが無い場合)は、これまでどおり録音開始の直後に始める。

### 参考: herdrから採れる情報(実測)

`herdr agent list` と `agent get` が返すのは `pane_id` / `workspace_id` / `agent`(CLI種別)/ `agent_session.value` / `agent_status` / `cwd` / `foreground_cwd` / `display_agent` / `terminal_id` / `terminal_title`、そして `name` である。

`name` は **`herdr agent start <NAME>` で起こしたagentにだけ付く**。利用者がペインで `claude` と打って始めたセッションには付かない。段4の実測では、owleryの3ペインはいずれも `name` が無く、`herdr agent start` で起こした検証用の2ペインだけが名前を返した。会議前に人が用意するペインは前者であることが多いので、agent名を接続先の主キーにはしない。指せるのは実質 `cwd` か `display_agent` か `pane_id` である。

段1では「`agent start` の名前はどちらにも返らない」と書いたが、これは名前の付いていないペインだけを観測した誤りだった。準備済みセッションはKIKIGAKIが `agent start` で起こすので `name` が付く。台帳の同一性判定には従来どおり pane・workspace・session・terminal を使い、`name` は診断の手掛かりに留める。

## 録音開始時の自動送信

`autoStart = true` のプロファイルがあれば、録音開始で既存の `startAISchedule` を呼ぶ。プロンプトは `autoPrompt`、間隔は `autoIntervalMinutes`、作業許可は `allowWork`、録音停止時の最後の1回はON。既存契約どおり即時送信はせず、開始から1間隔後を初回期限にする。

紐づけシートを出した場合は、その選択が終わってから始める。詳しくは上の「autoStartとの順序」を参照する。準備済みを使わない選択なら、従来どおり初回送信時にセッションを起こす。

開始後の操作は既存と同じ。「自動送信を停止」で録音を続けたまま止められ、設定を変えるにはいったん止めてシートを開き直す。状態行は「自動送信 3分 · 次 12:34 · 議事録へ」とし、宛先を含める。稼働状態は新会議・再起動で引き継がない。

## データ構造と保存

### 会議に1つの会話、プロファイルごとのチャネル

`AIConversationController` は会議に1つのまま残し、内部に**チャネル**をプロファイル分持つ。チャネルが持つのは `AIStreamHistory`、世代、`AISessionRecord`、`AIHerdrConnection`、接続状態、固定した設定、警告である。

controllerをプロファイルごとに複数へ分ける案は採らない。`AIConversation` が `request.number == index + 1` を復号時に検証しており、`archive.original.ai` も1つの会話を前提にしている。分けると通し番号・Markdown生成・保存・登録簿の再設計が連鎖する。受信箱はrequest ID単位なので、そもそも分ける必要がない。

チャネル化で変える判定は次の3つ。

- `canSend`: 現在は現世代の返事待ちを会話全体から探している。**そのチャネルの世代に属するrequestだけ**で判定する。これが手動と自動を別プロファイルで同時に走らせる根拠になる。
- `prepare` の設定等価性検証: チャネルが固定した設定とだけ比較する。
- `scanHooks` の休止判定: 受信箱は会議で1つなので、**どのチャネルの観測かを先に決めてから検証する**。チャネルごとに自分のproviderで検証すると、相手側CLIの正常なフックが不正イベントに化ける(世代番号が並ぶと必ず起きる)。準備済みセッションもKIKIGAKIが起こすのでフックは来る。紐づける際に、そのチャネルのフック用トークンを台帳の値へ引き継ぐ。
- 送信の進行(Task・実行ID・進捗・取消)もチャネルごとに持つ。会議に1つだと、Aの確定待ちや起動待ちの間Bへ送れない。会話への保存はMainActor上の直列処理のままにする。
- 警告の解消: 結果が届いた枠と世代を照合し、**その結果で解消できる警告だけ**を消す。Bの回答でAの送達不明を消さない。

`AIRecordStore.Record` は会議に1つのまま。`saveResult` `savedConversation` `needsRecovery` と登録簿の扱いは変えない。

警告は会議に1つの文字列として出す。プロファイルが2つ以上ある会議だけ「議事録: 送達を確認できません」のように名前を添える。表示の系統を増やさずに、どの宛先の話かを示せる。

### パスとenvelope

session recordの置き場を `ai/sessions/<slot>/<generation>.json` へ変える。`<slot>` は会議開始時にプロファイルへ割り当てた1始まりの整数で、設定の並び順から作る。`name` は日本語や記号を含むためパスへ持ち込まない。

ただし**プロファイルが1つだけの会議は従来の平置き** `ai/sessions/<generation>.json` のままにする。単一プロファイルの設定でファイル配置が動くと、旧会議と新会議で形が食い違う理由がないのに増える。Claudeの `--settings` もsession recordの隣へ置き、同じ規則で枝に入る。

**同梱CLIも両方の形を解釈する。** CLIは `--session` のパスから保存先の根を割り出しており、平置きを前提に決め打ちで5階層を遡っていた。枝を切った会議ではここが合わずに `unsafe_file` となり、段4の実herdrで返送が全滅した。アプリのテストはCLIを実行しないので落ちず、CLIのテストは平置きしか作っていなかった。枝の有無を見て遡る階層を変え、両方の形をCLIのテストで固定した。

`AIParticipantContext` に任意キー `profile`(表示名)と `profile_slot`(整数)を足す。`trigger` と同じ扱いで、`schema_version` は1のまま、欠損は既定プロファイル・slot 1として読む。単一プロファイルの会議ではこの2つも付けない。片方だけの指定は拒否する。`AIEnvelope.validate` の `sessionPath` 検証は、slotがあれば `ai/sessions/<slot>/<generation>.json`、無ければ従来の `ai/sessions/<generation>.json` を要求する。

manifestは `schemaVersion` を2へ上げ、`config` を `profiles: [ResolvedAIProfile]` の配列にする。schemaVersion 1のmanifestは、slot 1・`name` を参加者名としたプロファイル1つとして読む。

`.kikigaki-context/<meeting>/ai/` の `state.json` `archive.json` `requests/` `inbox/` `generation.json` は形も置き場も変えない。`generation.json` だけはチャネル別になるので `ai/sessions/<slot>/generation.json` へ移す。

### 準備済みセッションの台帳

`~/Library/Application Support/KIKIGAKI/ai-prepared.json` を新しく置く。会議の登録簿 `ai-roots.json` とは分ける。片方が壊れてももう片方の機能を止めないため。

```json
{
  "schema_version": 1,
  "sessions": [
    {
      "id": "準備UUID",
      "profile_slot": 2,
      "profile_name": "議事録",
      "started_at": "2026-09-09T13:05:00+09:00",
      "config": { "…ResolvedAIConfigと同じ固定値…" },
      "connection": { "workspaceID": "w6G", "paneID": "w6G:p1", "provider": "claude" },
      "token": "フック用トークン",
      "bound": { "meeting_id": "会議UUID", "profile_slot": 2 }
    }
  ]
}
```

`bound` が無ければ未紐づけ。紐づけると `bound` を書き、以後は一覧に出さない。書き込みは会議の登録簿と同じく原子的に行い、保存が成功するまで公開状態を変えない。

紐づけの瞬間にやることは、台帳の `bound` を書くことと、その接続を会議側の `ai/sessions/<slot>/1.json` へ書き写すことの2つである。**会議側の保存が成功してから台帳へ `bound` を書く。** 逆順にすると、台帳では使用済みなのに会議側に接続が無い行が残る。途中で落ちた場合は未紐づけのまま残り、もう一度選べる。

起動時は台帳を読み、各行の接続を `agent get` で確かめる。消えていれば行を落とす。確かめられない(herdrへ繋がらない)場合は落とさず、接続状態を不明として一覧に残す。

## 互換

- 単数 `[ai]` の設定はそのまま動く。slot 1、`name` は参加者名。
- 旧manifest(schemaVersion 1)を持つ会議は回収できる。旧requestは `profile` を持たないので slot 1 として表示し、旧 `sessionPath` 形式で検証する。
- 旧 `state.json` と `archive.json` はそのまま読める。`AIConversation` の形を変えない。
- 旧 `ai/sessions/<generation>.json` は残したまま読む。新規も、プロファイルが1つだけの会議は同じ平置きへ書き、2つ以上のときだけ枝を切る。同じ会議を新旧アプリで交互に開く運用は想定しない。
- 配布用Skillの契約は変えない。envelopeの追加キーは既知の任意キーとして無視されてよい。
- 台帳 `ai-prepared.json` が無い状態は「準備済みが1件も無い」と同じに扱う。旧版から上げたときに何も壊れない。
- `attach` と `displayAgent` を書いた設定は**設定エラーにする**。黙って無視すると、接続するつもりの設定で新規起動が始まる。取り下げた旨と移行先をメッセージに書く。

## 検証する境界

保証しないことを先に書く。

- **準備中にAIが何を読んだかをKIKIGAKIは知らない。** 下ごしらえの中身と品質は利用者とAIの間の話で、会議の受領基準にも保存物にも入らない。
- 準備済みセッションのペインは、紐づけるまでの間に利用者が別の用途に使える。KIKIGAKIはそれを検知しない。紐づけた後は既存の同一性判定(pane・workspace・session・terminal)で置き換えを見つける。
- 複数プロファイルへ同時に送っても、AI同士は互いの回答を見ない。同じ会議の同じ範囲を別々に読むだけである。
- 破棄はKIKIGAKIの台帳から外すだけで、外部プロセスの終了を保証しない。
- 準備済みを何件まで溜められるかに上限を置かない。溜まりすぎた場合の整理は利用者が行う。
- 設定の等価性は `ResolvedAIConfig` の一致で見るだけで、AI側が実際にどう起動しているかは確かめない。利用者がペインで別のことをしていても検知しない。

## 対象外

- 3つ以上のプロファイルを自動送信で同時に回すこと。自動送信の状態機械は会議に1つのままにする。
- 利用者が手で起こした既存herdrペインへ接続すること。段5で取り下げた。
- 準備済みセッションへKIKIGAKIから下ごしらえの指示を送ること。**起こすだけ**にして、何をさせるかは利用者がペインで指示する。会議に紐づかないうちは送信の記録も残らないため、KIKIGAKIが送ると追跡できない依頼が増える。
- 紐づけ済みのセッションを別の会議へ付け替えること。会議とチャネルの対応は紐づけ後に動かさない。
- CLIの設定・サンドボックス・信頼設定をKIKIGAKIが書き換えること。
- プロファイルごとのホットキー。既存の1つで既定プロファイルのシートを開く。
- 音声からの宛先自動判別。宛名で呼ばれたAIへ自動で振り分けることはしない。

## 採用した判断

段1のレビューで決めた。段2はこの形で実装してある。

- **`autoStart` は配列全体で1つまで。** 自動送信の状態機械 `AIScheduleState` は会議に1つで、複数同時は期限・失敗回数・最後の1回の権利をすべて多重化する。必要なら段を分ける。
- **プロファイルの定義は固定値としてmanifestへ残す。** requestのenvelopeがプロファイルを参照するので、記録の側に定義が無いと過去会議を復元できない。準備済みセッションを紐づけた場合も、そのプロファイルの固定値をmanifestへ書く。
- **切断したチャネルは「作り直す」で新しい世代を起こせる。** KIKIGAKIが起動する形に戻したので、この操作は既存の契約のまま使える。段3で接続型に限って隠していた判定は、接続案の取り下げとともに外す。
- **`extraArgs` での effort 指定は設定エラーにする。** 受理すると翻訳した引数との順序依存になり、どちらが効くか読めない。移行は1行の書き換えで済む。
- **`name` の既定は参加者名。** 重複したときだけ明示を必須にする。画面のポップアップは宛名で識別するのが自然で、設定の記述量も増えない。
- **ホットキーはプロファイルごとに持たない。** 既存の1つで既定プロファイルのシートを開き、宛先はシート内で選ぶ。プロファイル数だけ予約すると録音・一時停止との衝突検証が組み合わせで増える。

## 決めた振る舞い

段5のレビューで決めた。段6はこの形で実装してある。

- **同じプロファイルの準備済みが複数あるときは、最も古い1件を初期選択にする。** 連続する会議のために先に用意したものから順に使うのが自然で、余った新しいほうは次の会議へ回せる。
- **紐づけシートで「新規に起動する」を選んでも、未紐づけの準備済みはそのまま残す。** 次の会議で使えるし、破棄を明示操作にしたほうが事故が少ない。
- **準備済みの一覧は準備シートと同じ画面の下半分に置く。** 起こす操作と溜まっているものの確認は同じ関心で、画面を分けるとどこにあるか分からなくなる。
- **紐づけシートを出している間に録音を停止したら、シートを閉じて紐づけずに終える。** 準備済みは残す。停止操作を利用者の入力待ちで止めない。

## 判断依頼

1. **「AIセッションを準備…」を待機中のどこに置くか**。推奨はメニューバーのメニューに置き、書き起こしウィンドウのフッターにも録音中だけ出す。理由: 待機中は書き起こしウィンドウを開いていないことが多く、フッターだけだと辿り着けない。代替はウィンドウ上部の常設ボタンだが、録音の主操作の近くに会議外の操作を混ぜたくない。画面の見え方はクロディーヌのモックと併せて確認する。
