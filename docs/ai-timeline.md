# AIを会話の参加者として並べる

書き起こしの中に置いていた畳んだ印をやめ、AIの送信と返事を人の発話と同じ行の形で時系列に並べる設計。会議参加モードの契約は [ai-participant.md](ai-participant.md)、定期自動送信は [ai-scheduled.md](ai-scheduled.md)、返事本文の描画は [ai-markdown.md](ai-markdown.md) を引き継ぐ。この文書は [ai-participant.md](ai-participant.md) の「画面と記録」のうち、印の表題・開閉・抜粋に関する部分だけを改める。

## 変える理由と変えない範囲

タダシの申告は「本文がすぐ見えない」「送信と返事が別行」「発話に割り込む」「状態が分からない」の4点で、備考は「AIのやりとりを人間のやりとりと別々にしているから分かりにくい」。原因は、AIだけが別種の畳んだ1行として置かれ、読むのに開く操作が要ることにある。実寸モック3案から案Aを採用した。正とするモックは `plan-a-normal.png` と `plan-a-busy.png`。

変えないものを先に固定する。

- 会議Markdownの `## AIとのやりとり` と `## 書き起こし` の形式。表示だけの変更で、保存物の互換は保つ
- 受信箱・request・envelope・保存済みJSONの形式と `schema_version`
- AIを `Utterance` にしないこと。AIの行は書き起こし・snapshot・AI文脈・コピー範囲のいずれにも入らない
- 声の送信印を `voiceUtteranceStart` の直下へ置く規則。`AIRequest.voiceAnchorIndex(in:)` をそのまま使う
- フッターの4種のピルと「AIへ渡す会話」の行。移動先の行IDだけを差し替える
- 到着時に前面化しないこと。末尾追従中はAIの行と状態変化も人の発話と同じく追い、上へスクロール中・検索中だけ位置を動かさない

## 行の種類

`AIMarkRow` の2種類の印を、4種類の行へ置き換える。

| 行 | いつ出るか | 形 |
|---|---|---|
| 送信の細い1行 | 声からの送信、および自動送信 | `└ 迅雷へ送信 · 4発言 · 14:06:24`。11pt薄墨。自動は「迅雷へ自動送信」とし、薄墨を65%へ落とす |
| 人側の送信行 | 問い欄へ入力した手動送信、確認への返答 | 発話と同じ枠。アバター・名前・時刻・本文は送信文全文。右端に宛名のピル |
| AIの行 | 送信試行済みで取消・送信前失敗でないrequest | アバター・名前・チップ・時刻・本文。返事待ちの間は同じ行を「考え中…」で出す |
| 失敗の帯 | 送信できなかったrequest | 朱の細い1行。理由と「再送」と時刻。返送された失敗は未読の印も置き、帯の下へ本文を全部出す |

AIの行は既定で展開する。畳む操作は持たせない。畳んだ状態・抜粋・`▸`の三角・「送信文:」の見出しは全て廃止する。

### 送信の表し方の分岐

送信の形は `question_source` だけでは決まらない。自動送信は `autoPrompt` を送るので `question_source` はtypedだが、人側の行にはしない。

| 条件 | 送信の行 | 返事の上の引用 |
|---|---|---|
| `trigger == .scheduled` | 細い1行「迅雷へ自動送信」。日時順に置く | なし |
| `question_source == .voice` | 細い1行「迅雷へ送信」。`voiceAnchorIndex` の発話の直下へ置く | なし。発話そのものが送信文 |
| 上記以外の手動送信 | 人側の送信行 | あり |

確認への返答は手動のtypedなので人側の送信行になる。`in_reply_to_request_id` を持つ送信行の名前の右へ「#1への返答」を薄墨で添える。

### 返事の上の1行引用

キーボード入力の送信に限り、AIの行の本文の上へ送信文を1行の引用として置く。薄墨・12pt・本文から12pt字下げし、空いた左へ `rule` の2pt罫を置く。末尾は省略する。送信行と返事行の間に発話が入るため、何への返事かを返事側だけで読めるようにする。クリックで全文へ伸ばし、再クリックで1行へ戻す。開閉状態は行ビューが保持し、発話追加・既読・改名では失わない。

**送信行と返事行が同じ位置で隣り合うときは引用を出さない。** 間に何も入らなければ同じ文が2回続くだけで、引用の目的が消える。送って即待ちは会議中の最頻ケースなので、隣接は例外ではなく既定になる。判定はCoreの並べ替え後に行い、描画側に残さない。

### AIの行の中身

| 部品 | 内容 |
|---|---|
| アバター | プロファイルの `avatar` 画像。省略・取得失敗時は参加者名の頭文字とAI専用色の紫。返事待ちの間は破線の丸 |
| 名前 | `participant.participantName`。`AIViewState.participant` ではなくrequestの固定値を読む |
| チップ | 手動は「AI」、`trigger == .scheduled` は「自動」。10pt・`rule` の枠・薄墨 |
| 時刻 | 到着時刻 `resultReceivedAt`。返事待ちの間は出さない |
| 状態ピル | 未読は朱の塗り、確認待ちは金の塗り、返事待ちは薄墨の枠。既読の通常回はピルなし。塗りの文字色は地の色に合わせ、金地では `ink` にする |
| 本文 | `MarkdownBodyView`。返事待ちは「考え中…」の薄墨、確認質問は本文の先頭に `?` を外付け |
| 注記 | 必要なときだけ本文の下へ薄墨1行。「取消後の返事」「旧接続からの返事」「#Nで返答」「返送未確認」 |
| 操作 | 確認待ちの「返答する」は本文の下、返事待ちの「取消」は「考え中…」と同じ行の右端 |

未読は行全体へ11%の地色と3ptの左帯を敷き、既読で消して `muted` へ戻す。既存の縦罫は廃止し、帯へ寄せる。**確認待ちの金の帯とピルだけは既読では消さず、返答するまで残す。** 無効状態で面を足さない原則は守り、通常の既読行には枠も地も置かない。

確認質問の `?` は状態ではなく本文が問いであることの印なので、返答したあとも `rule` へ落として残す。

失敗は2種類あり、言い方を分ける。送信そのものができなかったものは「〜へ送信できませんでした」、モデルが返した失敗報告は「〜から失敗の報告」とし、**後者は帯の下へ本文を全部出す**。「一部の更新に失敗しました / 更新済み: A / 未更新: B」のような報告は、どこまで進んだかが画面から読めないと使えない。

送達不明は「考え中…」を出さないので、**取消は送信の行に置く**。他に取り消す場所がなく、`isAwaitingResult` が残る間は次の送信も止まる。取消は行の高さを変えない位置へ置く。結果が届いて取消が消えたときに行が縮むと、末尾を読んでいる利用者の画面が動く。

送信の詳細は細い1行と人側の送信行へ寄せる。「N発言」は常に出し、`作業許可なし`・`暫定末尾を含む`・`送達不明` は該当するときだけ ` · ` で連ねる。時刻範囲と秒と全文はtooltipへ置く。展開が無くなるため、これまで詳細欄にあった情報の置き場所はここになる。時刻は人の発話と同じ `HH:MM` にし、1本の時間軸に2つの桁数を混ぜない。

取消・送信準備中の送信行は、送れた送信と同じ重さで会話に残さない。面は足さず本文と記号の色を抜く。

## 並べ方

`TranscriptEntries.merge` は変えない。AIの行はUtteranceではないので、併合結果へ混ぜず、別の純関数で位置だけを決める。

`KikigakiCore/AITimeline.swift` に副作用のない `AITimeline.items(conversation:utterances:timeline:generation:)` を置く。返すのは表示に必要な値だけを持つ `AITimeline.Item` の列で、AppKit型・色・フォント・時刻の書式を含めない。時刻はDateのまま返す。

```swift
public enum AITimeline {
    public enum Kind: Equatable, Sendable {
        case sendLine(automatic: Bool)   // 細い1行
        case sendRow                     // 人側の送信行
        case reply(ReplyState)           // AIの行。waiting / answered / needsInput
        case failure(reason: String)     // 朱の帯
    }
    public enum Anchor: Equatable, Sendable {
        case afterUtterance(Int)   // 声の送信。voiceAnchorIndex の直下
        case at(Date)              // 日時順
        case tail                  // 末尾。返事待ちの行だけ
    }
    public struct Item: Equatable, Sendable {
        public let kind: Kind
        public let anchor: Anchor
        public let slot: Int       // 直前に置く発話の添字。-1は全発話より前
        ...
    }
}
```

`Item` は行が要る値を全て持つ。`participantName`・`automatic`・`date`・`question`・`parentNumber`・`body`・`notes`・`timeRange`・`isUnread`・`needsAnswer`・`rowID` で、描画側に判定を残さない。`notes` は「対象: 4発言」「作業許可なし」「暫定末尾を含む」「送達不明」「取消後の返事」などの完成した文字列にする。`AIRequest.automaticLabel` と同じく、表示用の短い文字列はCoreに置く。

そのため接続の観測も入力へ渡す。返事待ちの「ペインで確認してください」「接続が切れています」「返送未確認」は、`AIConnectionStatus` と未確認requestの集合から `notes` を作る。描画側で足すと、Coreへ集約する意味がなくなる。

順序の規則は次のとおり。

- `afterUtterance` はその発話の直後へ、同じ発話に複数あればrequest番号順に置く
- `at(date)` は**最初に自分より新しい発話の手前**へ置く。発話の日時は音声位置と投稿順で並ぶので単調とは限らず、最後の一致で探すと間の発話を飛び越える。**同時刻なら人が先で、AIはその後ろへ付く**
- 録音を停止した日時を入力に受け、それ以後に届いた返事は末尾へ置く。時計が飛んでも「停止後の返事は末尾」を保てるようにするため
- `tail` は全ての発話とAI行より後に置く。**返事待ちの行が上へ跳ねないようにするための規則**で、送信時刻の位置ではなく常に末尾側へ置く。返事が届いた時点で `at(resultReceivedAt)` へ変わり、そのときの末尾がそのまま確定位置になる
- 返事待ちが複数あるときは `sendAttemptedAt` の順に末尾へ並べる
- 同じ位置・同じ日時では送信が先。返事同士は**記録順** `resultOrder` で並べ、記録を持たない送信前の失敗を先頭へ置く。request番号ではない。最後に生成順で必ず全順序にする

`AIInlineMark` は廃止する。`AIBadgeKind.markID(_:)` の返す行IDは `requestID + "/send"` と `requestID + "/reply"` の2種類にし、未読・確認待ちは `/reply`、返事待ち・送達不明・失敗は該当する行のIDを返す。

## 行ビューと再利用

`TranscriptDocument` の再配置とアンカーの仕組みは変えない。行の同一性だけを整理する。

- 返事待ちの行と返事の行は**同じビュー・同じ行ID**にする。差し替えではなく状態更新にすることで、返事の到着で行が消えて生まれ直すことがなくなり、高さの変化がアンカーの候補から外れない
- 送信の細い1行・人側の送信行・失敗の帯もrequest単位のビューを再利用する。`aiRows[id]` の辞書は現在の `aiMarks` と同じ寿命規則にする
- 末尾追従中はAIの行追加と状態変化でも末尾を追う。AIだけの更新で `atBottom` を落とさず、上へスクロール中はアンカー、検索中は `followsBottom` により位置を保つ
- 引用行の開閉は `AIMarkRow.onToggle` と同じ経路を使い、開いた行の上端をその場に保ったまま `reflow` する
- 高さの計測は `MarkdownBodyView.height(for:)` を使い、`cellSize` と混在させない。幅が変わったときの再計測も既存どおり

上へスクロール中・検索中は到着で読んでいる位置を動かさない。行の追加位置が可視域より下なら現在の見出しを保ち、上なら `anchor.candidates` の生き残り行を基準に位置を戻す。遅れた返事が可視域より上へ入る場合も、このアンカーで高さの変化を吸収する。

## 既読

これまでの既読は「畳んだ印を開く」ことだった。展開が既定になるとこの操作が無くなるため、決定1のとおり、**行が可視域と重なった**状態でウィンドウがキーのまま連続1秒留まったら既読とし、未読ピルのクリックでも既読にする。

どの案でも次は共通にする。

- 既読は `AIConversationController.markRead` で保存する。UIだけで隠さない
- `trigger == .scheduled` かつansweredは、これまでどおり取り込み時点で既読として保存する。自動の返事に未読は付かない
- 確認待ちの金の帯と「返答する」は、既読とは独立に、返答されるまで残す
- 通知音の対象は変えない

## 検索・過去会議・複数プロファイル

- **検索**: `TranscriptWindowSearch` は `snapshot.utterances` だけを走査し、ヒットを `RowID` へ紐づける。AIの行はUtteranceではないので対象外のままにする。本文が常に見える形になると対象外であることは目立つが、このタスクでは扱わず別タスクへ切り出す
- **過去会議**: `AIPastMeetingsWindow` は発話を持たず、`AIInlineMark.ordered` の列だけを並べている。同じ行部品を使い、`utterances` を空として `AITimeline.items` を呼ぶ。発話が無いので `afterUtterance` は解決できず、その場合は `at(sendAttemptedAt)` へ落として日時順に置く。返事は同じく展開既定、操作は「返答する」を出さない読み取り専用のままにする。**枠ごとの世代・接続・未確認集合も現在の会議と同じ形で渡す。** 全体の値で塗ると、片方の宛先を作り直しただけで、もう片方の正常な返事まで「旧接続から」になる
- **複数プロファイル**: `feature/ai-profiles` は宛名をプロファイルごとに持ち、会議内の `#n` は全体で通す。この設計では宛名を `question.request.envelope.participant.participantName` からだけ読み、会議単位の既定値へ依存しない。細い1行と宛名ピルにその名前を入れれば、統合の順序に関係なく同じ結果になる。行の色は決定2のとおり全プロファイルで同色にする。統合順は本人が決めるので、この文書ではプロファイル側のAPIへ触れない

## 決定した論点

段1のレビューで7件とも下記のとおり採用した。

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 既読の成立条件 | 行が可視域と重なった状態で、ウィンドウがキーのまま連続1秒留まったら既読。加えて未読ピルのクリックでも既読にする | 展開の操作が無くなるので可視化で判定する。末尾追従で返事が可視域へ入った場合も同じ滞在条件を使う。上端ではなく重なりで見るのは、画面いっぱいの長い返事をスクロールしながら読む間ずっと対象から外れないようにするため |
| 2 | AIのアバター色 | `Washi` へAI専用色を1つ足す。複数プロファイルでも同色にし、名前で区別する | モックは枡3の藍緑を流用しているが、これは4人目の話者の色と同じで、4枡使う会議で人とAIが同色になる。プロファイルごとに色を配ると枡の色と衝突する組合せが増えるため、AIは1色に固定して名前で分ける |
| 3 | 人側の送信行の名前 | 「手入力」を流用せず、墨の丸に `paperplane` のアバター、名前は「AIへ送信」、右端のピルで宛名を出す | 「手入力」は会話へ残る投稿の固定名で、会議Markdownの `## 書き起こし` にも出る。AIへ送っただけの文が議事録に載っていると誤解される。行の形は決定どおり人側のまま変えない |
| 4 | 引用の全文の出し方 | クリックでその行を全文へ伸ばし、再クリックで1行へ戻す | ポップオーバーやtooltipは、本文と並べて読み比べられない。既存の開閉と同じ `reflow` の経路を使えるので、位置の保ち方も検証済みのものを流用できる |
| 5 | 「ペインを開く」の置き場所 | 行から外し、フッターへ1つだけ置く | 展開が既定になると全ての返事の行に同じボタンが並ぶ。接続の作り直しや保存の再試行は既にフッターにあり、接続の操作はそこへ揃う |
| 6 | AIの本文を検索対象へ入れるか | **このタスクの対象外**とし、別タスクにする | `SearchHit` は `RowID` と発話の添字に紐づいており、AIの行を入れると検索の設計自体が変わる。Markdown描画の `NSTextStorage` へのハイライトも別の作業になる。表示の刷新と同じ段で混ぜると、どちらの検証も薄くなる |
| 7 | 自動送信の返事待ちを行として出すか | 出す。人の送信と同じ「考え中…」の行にする | 「状態が分からない」が今回の対象で、自動だけ状態を隠すと3分ごとに理由の分からない行が生えることになる。目立たせないのはチップと薄墨で足りる |

### 段3のUIレビュー反映

クロディーヌのレビューで必須4・推奨7・任意6を受け、いずれも採用した。必須のうち3件は「設計どおりに書いたつもりが画面に出ていない」型だった。

- **引用の左罫と字下げが出ていなかった**。`alignmentRectInsets` は手動フレーム配置では参照されず、罫もボタンの内側に描いていたので文字に隠れていた。字下げをフレームで与え、罫は別のサブビューにした
- **送信行と返事行が隣接すると同じ文が2回出ていた**。上の引用の節のとおりCoreで落とす
- **自動送信の細い1行が2.6:1**だった。この地色では11ptを薄めて弱める余地がない。`Washi.muted` へ戻し、自動の区別は語に任せる
- **「AI」「自動」の印に枠が無かった**。混雑した画面では、自動の返事を人の依頼への返事と見分ける唯一の手掛かりがこの語になる。枠のピルにした
- 金地の白文字が3.25:1だったので、塗りピルの文字色を地の色で選ぶようにした。行のピルとフッターのバッジの両方
- 宛名から枠を外した。宛名はラベルで状態ではない。枠つきピルを状態専用に残し、枠の有無がそのまま「注意が要るか」になる
- **既読の可視判定を行と可視域の重なりに変えた**。上端だけを見ると、画面いっぱいの長い返事はスクロールしながら読んでいる間ずっと対象から外れる
- 時刻を人と同じ `HH:MM` に、取消・準備中の送信行の色を抜き、返答後も `?` を残し、親の注記を「#Nで返答」にした
- フッターの操作を行の操作と同じ枠のピルに揃えた。同じ「押すもの」が2種類の見え方をしていた
- 任意6件も採用した。「対象:」を落とし、失敗の帯を12ptにし、「取消」を「考え中…」の行の右端へ寄せ、読み取り専用で失敗の時刻が浮かないようにした
- **AIの色を紺から紫へ変えた**。4枡が埋まった実画面を撮ったところ、紺は4枡目の青緑と近い。紫は4色のいずれとも色相が離れる

### 段2のCore実装

`AITimeline.items` を実装した。`AIConversation` を走査し、requestごとに送信の要素を必ず1つ、返事・失敗の要素を条件付きで1つ作る。

- 送信の形は `trigger == .scheduled` → 細い1行、`question_source == .voice` → 細い1行、それ以外 → 人側の行の順に決める。**自動送信は `question_source` がtypedなので、この順序でないと人側の行になってしまう**
- 返事側は失敗・結果あり・返事待ちの順に判定する。`delivery_unknown` は成否が分からないので要素を作らず、送信の注記へ「送達不明」を足すだけにする。「考え中…」を出すと送れた前提の嘘になる
- 失敗の判定は状態だけでなく**結果の種類も見る**。取消後に届いた結果は状態が `cancelled` のまま残るので、状態だけを見ると失敗が通常の返事に化ける
- 取消後に届いた結果は要素を作り、「取消後の返事」の注記を付ける。`AIInlineMark` の既存の扱いを引き継ぐ。失敗の帯は1行なので、この注記も同じ行へ連ねる
- 失敗と返事の表示時刻は到着時刻。到着が無い送信前の失敗は、固定した送信時刻を出す
- 引用は `sendRow` のときだけ非空にする。声は発話そのものが送信文で、自動は毎回同じ定型文になる
- 並べ替えは `(slot, rank, 日時, 送信か返事か, 記録順, request番号, 生成順)` で全順序にする。`rank` は afterUtterance・at・tail の順。同じ入力からは必ず同じ列になる

段2はGPT-6のクロスレビューを受け、順序・分類・情報の受け渡しを直した。指摘は同時刻の返事が記録順を失うこと、日時が単調でない発話列で挿入位置が変わること、取消後の失敗を通常の返事に分類すること、`Item` だけでは詳細と状態を作れないこと、送信前失敗の時刻がnilになること、文書の同時刻の順序が実装と逆であること。いずれも上記へ反映し、再現例をテストへ足した。

`AIInlineMark` と `AIMarkRow` はまだ残してあり、差し替えは段3で行う。段2では既存の描画経路に触れていない。

### 段3の描画実装

`Sources/Kikigaki/AITimelineRows.swift` に `AISendLineRow`・`AITypedSendRow`・`AIReplyRow` を置き、`AIInlineMark` と `AIMarkRow` を削除した。`AIReplyRow` が返事待ち・返事・確認質問・失敗の帯を1つのビューで扱い、行IDを共有する。

- **AIの色**: `Washi.ai` を1色追加した。`AvatarView` に `accent` と `glyph` を足し、話者枡の色と記号を差し替えられるようにした
- **人側の送信行**: 墨の丸に `paperplane.fill`、名前は「AIへ送信」、右端に宛名の枠ピル。「手入力」の名前と鉛筆は使わない
- **行の操作**: 「返答する」「取消」「再送」は枠のピルで描く。押せない場面ではボタン自体を出さないので、無効時に面を足す状態を作らない
- **既読**: `AIReadWatcher` が0.25秒ごとに走り、行が可視域と重なった状態でウィンドウを見ているまま連続1秒留まったら `onReadAI` を呼ぶ。未読の印を押しても既読になる。走査は画面の上から順で、既読の保存が再構築を呼ぶので走査を終えてから通知する。未読が無くなればタイマーを止める
- **確認質問**: 未読でも返答済みなら金の帯を外す。未読の朱にはしない。既存の `AIBadgeKind.unread` が確認を除いているのに合わせる
- **「ペインを開く」**: 書き起こしウィンドウのフッターと過去会議ウィンドウの操作列へ1つだけ置く

実画面で見つけて直したもの。`AIStatusPill` の初期表題が `NSButton` 既定の「Button」のままだったこと、失敗の帯に確定時刻が無かったこと、返事待ちに「AI」の印と時刻が出ていたことの3点。

`MarkdownBodyView` の高さを測る前に、表示と同じ幅の枠を与えるようにした。**幅0のまま最初に測ると、表やコードを含む返事の高さが11倍ほどに跳ね上がり、その値が幅ごとの計測キャッシュへ残る。** 畳んだ印だった頃は、展開まで測らなかったので表に出ていなかった。

### 段3のクロスレビュー反映

GPT-6のクロスレビューで中4件・低3件を受け、既読・再送・回帰テストを直した。

- **返送された失敗も既読の対象**にした。Coreは `.failed` の結果を未読にするのに、行が可視判定から外れ印も無く、未読件数と「前の会議に返事あり」が残り続けていた。帯の中へ未読の印を置き、可視化の対象にも含める。**送信前の失敗はそもそも未読にならない**ので印は出ない
- **既読の判定を `AIReadWatcher` へ切り出し**、書き起こしウィンドウと過去会議ウィンドウで共有する。過去会議には可視化の経路が無く、確認質問は既読にする手段が無かった。会議を切り替えたら滞在時間を捨てる
- 滞在時間は**単調時計**で測り、キー喪失・最小化・アプリの非活性で数え直す。可視域が変わった時点でも外れた行の時間を捨てる。0.25秒の評価の合間に出入りした行の時間を足し続けないため。タイマーは**common modes** へ入れ、スクロールのドラッグ中も止めない
- **「再送」は元requestを渡す**。`onResendAI` を新設し、送信文・宛先・親への対応付け・作業許可を戻したシートを開く。以前は新規の問いを開いていたので、別の下書きが入っていると違う依頼になり、確認への返答だった場合は親を失っていた。**宛先はシートへ固定の枠として渡す。** 選択欄を隠すだけでは `owningSlot` が選択値を見るので、送信先と取消先が食い違い、取り消したはずの依頼が送信され得る
- タイマーはウォッチャーの破棄で止め、参照先が消えたコールバックでも自分を止める
- **確認待ちの金の帯は返答まで残す**。実装が既読で消していたのを文書へ合わせた。既読の管理は帯とは別で、可視化と印が担う

確認への返答が失敗・取消で終わったときは、**同じ確認へ送り直せる**ようにCoreの契約を変えた。親の `answeredByRequestID` が失敗した返答を指したままだと、再送が「返答済み」として `AIError.mismatch` で拒否される。失敗・取消で終わった返答は返答済みとして数えず、参照を新しいrequestへ付け替える。復元時の検証も、付け替えで外れた古い返答が失敗・取消であることを条件に許す。

この「返答済みか」の判定は `AIQuestion.isAnswered(_:in:)` に1つだけ置き、**表示・件数・自動送信の抑止・保存のすべてがここを通る**。`answeredByRequestID` の有無だけを見る場所を残すと、送り直せる状態なのに「返答する」と確認待ちの件数が消える。

回帰テストは実コントロールを通すようにした。印の表題と有効・無効、失敗の帯の時刻、返事待ちのチップと時刻の非表示、引用の実クリックと開閉の保持、待機から返事への同一ビューでの変化、非キー状態を挟んだ中断、過去会議の既読の配線を確認する。
