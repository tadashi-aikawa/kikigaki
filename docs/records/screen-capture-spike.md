# 画面の記録の試作の検証記録

2026-11-09の第0フェーズの独立試作の検証記録。現行の仕様ではない。試作CLIの操作は[独立試作のREADME](../../experiments/screen-capture/README.md)を参照する。設計の前提はowlery Vaultの「KIKIGAKI 会議中の画面の記録の設計方針案 2026-11-09」。

## 結論

**成り立つ。設計案の2つの判定は、縮小画像を横128マスに上げ、メニューバーを比較から外せば、合成画面では1文字の修正を除いて取りこぼし0・余分0にできた。**

- 撮る契機の初期値は下の表のとおり。合成の会議画面7本と、小さく動き続けるだけの画面計40分で当てた
  - 取りこぼし: 1文字の修正だけ。会議画面7本の全てで取りこぼした
  - 余分: 0枚。点滅するカーソル・秒まで出す時計・回る印を計40分流しても増えなかった
- 1文字の修正は拾わない側に倒した。設計案の「小さな文字の修正が1枚」は満たさない
  - 理由: しきい値を1文字に届くまで下げた組では、点滅するカーソル・時計・回る印で余分が出続けた。同じ11本で余分236枚になり、AIへ渡す画像として使えない
  - 補い: 保存する価値は最後に保存した画像と比べるので、修正が数語に積もった時点で拾う。1行の入力は全本で拾えた
  - 決定: タダシが2026-11-09に承認した。実画面でノイズによる余分が出るなら、しきい値をさらに上げてよい
- 設計案の縮小画像64×36は粗すぎた。横128マスにする
- メニューバーを比較から外す。設計案に無かった判定
  - 理由: 時計の分が変わるたびに保存しないため
- 小さく動き続けるマスを外す判定は試したが、初期値には入れない
  - 理由: 大きな画面に小さな文字のページを続けて送ると、ページの中身まで外れて取りこぼした。効き方が画面と文字の大きさに左右される
  - 受け入れる限界: 回る印のような小さなアニメーションがあると、落ち着くまでの保存が最大12秒遅れた。大きなアニメーションは落ち着かず、止まるまで保存しない。設計案のとおり「いま撮る」で補う
- libwebpはUTSUSHIEと同じパッケージで、本体の `make-app.sh` に変更なしで収まった
- WebP品質80・1x寸法で、Retinaを縮めた画面の16pt相当の文字が読めた。1枚は文字の多い画面で約220〜310KB、スライドで約30KB
- 負荷: 文字起こし・話者判別と併走させても、監視側がCPU約6%・メモリ約130MBで、KIKIGAKI側のCPUに差は出なかった
- 実画面5分半では、1.5秒以上映した状態に取りこぼしは無かった。保存45枚のうち16枚は、状態が随時更新されるparliamentの画面の小さな更新だった
  - 保存の最短間隔と、しきい値をさらに上げるかは第1フェーズで実会議に使って決める
- 題の取り方は、実画面で映っていたアプリ・ページと合った。全画面のChromeだけは題が空で、アプリ名だけになった
- 許可の後に再起動は要らなかった。ただし同じプロセスの `CGPreflightScreenCaptureAccess` は古い値を返すので、許可の判定には使わない
- 未実測の項目は「残り」に挙げる

## 撮る契機の初期値

| 値 | 初期値 | 意味 |
| --- | --- | --- |
| 縮小画像の幅 | 128マス | 高さは画面の縦横比から決める。16:9なら128×72 |
| マスの差 | 輝度8 | 1マスの平均輝度の差がこれを超えたら変わったとみなす |
| 動き | 変わったマス0.02% | 直前の観測フレームと比べる。128×72で約2マス |
| 保存する価値 | 変わったマス0.1% | 最後に保存した画像と比べる。128×72で約9マス |
| 落ち着く秒数 | 1.5秒 | 設計案のまま |
| メニューバー | 比較から外す | 高さは `NSScreen` の `frame` と `visibleFrame` の差 |

- 動きのしきい値は保存する価値のしきい値以下にする
  - 理由: 逆にすると、動きに数えない小さなアニメーションが保存した画像との差だけを超え、落ち着くたびに保存し続ける
- 保存の判定は、`idle` の間も監視の開始から0.25秒刻みのタイマーで進める
- 第1フェーズへ持ち込む約束。試作では一部だけ確かめた
  - 比較の基準は、画像の保存に成功してから更新する。試作は保存を決めた時点で更新しており、保存に失敗すると同じ画面を保存済みとみなす
  - `blank`・`suspended`・停止の間は判定を止め、保留中のフレームを後から保存しない。復帰した最初のフレームは待たずに保存する。試作で実装し、自己点検で確かめた。観測ログにも残し、当て直しで同じ初期化を再現する
  - 題の候補は、画像と同じフレームを受け取った時点で取る。試作で実装した

## 合成で当てた筋書きと結果

正解の分かる会議画面を `synth` で合成し、1秒ごとの観測を位相と±0.2秒の揺らぎを変えて複数本作った。筋書きと正解の区間は `Synth.swift` の冒頭。

- 会議の筋書き(215秒): 静止スライド、0.6秒のフェードで送る、細かい文書へ即時に送る、1文字の修正、1行の入力、10秒の連続スクロール、画面の約22%を占める動画、秒まで出す時計、回る印、通知バナー、1.5秒ごとに3回続けて送ってから6.5秒・9秒・20秒ずつ見る。文書の間はカーソルが点滅する
  - 正解の区間: フェードの途中と動画の再生中・停止後は区間を分けた。遷移の途中の1枚だけで合格にしないため
- 動き続ける筋書き(600秒): 点滅するカーソルのある文書、秒の時計のあるスライド、回る印のあるスライドを各200秒。正解は各1枚
- 画面: 1920×1080、3840×1600に同じ見た目を拡大したもの、3840×1600に等倍の文字を描いたもの
  - 等倍の文字の画面は、横長の外部ディスプレイに小さな文字のウィンドウを出した場面。マス1つに入る文字の量が最も少ない
- 本数: 会議の筋書き7本(1920×1080が3本、ほかが各2本)、動き続ける筋書き4本(計40分)

| 組 | 取りこぼし | 余分 | 備考 |
| --- | --- | --- | --- |
| 初期値 | 7 | 0 | 取りこぼしは全て1文字の修正。回る印のあるスライドの保存が1〜12秒遅れた |
| 初期値に、小さく動き続けるマスを外す判定を足す | 9 | 0 | 等倍の文字の画面で、続けて送った後に6.5秒見たページを2本とも取りこぼした |
| 動きと保存のしきい値を0.01%へ下げた組(幅256・差16)。1920×1080で4マスの変化から保存する | 2 | 236 | 余分は点滅するカーソル・時計・回る印 |

- 外すマスの判定は、直前との差が5%以下のフレームだけで数える形まで試した
  - 結果: 横長に等倍の文字では、ページ送り1回の差が5%を下回り、ページの中身が外れた
- 記録: 総当たりの出力は `experiments/screen-capture/work/r6/` の `sweep-*.txt`。gitで無視される手元だけの証拠
- 限界: 合成はCoreTextの描画で、Keynoteの切替効果・ブラウザの滑らかなスクロール・実際の動画の圧縮ノイズは無い。実画面での確認は「残り」に挙げる

## 負荷

KIKIGAKIのreplay(等倍・話者判別あり、187秒の音声)を流し、同時に `watch --no-write` でEV3895(3840×1600、1x)を初期値で180秒監視した。`top` を2秒ごとに取り、replayだけの回と比べた。

| 項目 | replayだけ | 監視を併走 |
| --- | --- | --- |
| KIKIGAKIのCPU | 平均17.7% | 平均17.4% |
| 試作のCPU | − | 平均5.6%。監視開始からのrusageでは180秒で10.3秒、5.7% |
| 試作のメモリ | − | 約5秒ごとの標本で最大127MB(`phys_footprint`) |
| `top` のPOWER | KIKIGAKI 17.9 | KIKIGAKI 17.4、試作 5.6 |

- 内訳: 観測181枚。画面が毎秒変わり、idleは無かった。縮小が1枚平均43ms、符号化が1枚平均204ms・約300KB
  - CPUの大半は縮小。等倍の輝度画像へ描いてから平均している。第1フェーズでは縮小の手前で解像度を落として軽くできる
- KIKIGAKIのCPUに差は出なかった。replayは最後まで完走し、本文も保存された
- 条件: 監視中のEV3895には、タダシの作業中の画面が映っていた。`--no-write` なので画像も縮小画像も残していない
- 実画面での保存判定: 180秒で13回。映っていたのは状態が随時更新されるparliamentの画面
  - 内容の妥当性: 画像を残していないので、13回が意味のある変化だったかは確かめられない。実画面の確認は `--keep-all` で行う
  - 気づき: 常に更新される画面を映すと1時間で数百枚になりうる。保存の最短間隔を設けるかは第1フェーズで決める
- 限界: 電力は `top` のPOWER(エネルギー影響の相対値)だけ。`powermetrics` の実測は管理者権限が要るので行っていない。内蔵Retinaの監視は測っていない。画素数が最も多いEV3895を上限とみなした
- 1回目の計測は判定と集計を直す前のもので、数値の比較には使わない。手元の `work/load/*-run1*` に残した

## 実画面

タダシがEV3895で、全画面のスライド送り・ブラウザのスクロール・YouTubeの動画・ターミナルでの入力・ウィンドウの切り替えを5分半映し、`watch --keep-all` の初期値で監視した。全211フレームと保存45枚を突き合わせた。

| 場面 | 結果 |
| --- | --- |
| スライドの送りとクリックでの段階表示 | 1.5秒以上見た状態は全て1枚ずつ保存した(14枚)。1秒ほどで続けて出した段階は、出し切った状態の1枚にまとまった |
| 全画面を抜ける直前に1秒ずつ送った2枚 | 保存しなかった。落ち着く1.5秒に届いていない |
| ブラウザのスクロール | 止めるたびに1枚、計5枚 |
| YouTubeの動画の再生 | 再生中は保存しなかった |
| ウィンドウの切り替え | 切り替えるたびに1枚。題は映っていたアプリ・ページと合っていた |
| 状態が随時更新されるparliamentの画面 | 小さな通知やポップアップが出るたびに保存した。45枚のうち16枚 |

- 取りこぼし: 1.5秒以上映した状態では見つからなかった
- 余分: 意味の薄い保存は、parliamentの画面の小さな更新だけだった
  - 決定の備考どおり、第1フェーズで実会議に使って多ければしきい値を上げる。保存の最短間隔もそこで決める
- 題: 全画面のChromeは題が空で、アプリ名の「Google Chrome」だけになった。ウィンドウ表示のChrome・Ghostty・parliamentは題まで合っていた
- 容量: 45枚で計9.6MB、平均218KB、最大483KB
- 負荷: `--keep-all` で全フレームを符号化したので、CPU19%・標本のメモリ最大449MBは負荷の評価に使わない。初期値の負荷は負荷の節

## 許可

独立.app2つを `open` で起動し、タダシがシステム設定で許可した。

| 項目 | 結果 |
| --- | --- |
| 初回 | 未許可のまま `CGRequestScreenCaptureAccess` で要求し、タダシがシステム設定で許可した |
| 許可の後の再起動 | 要らなかった。同じプロセスのまま、許可の17〜24秒後にSCShareableContentの取得と撮影が成功した |
| 同じプロセスの `CGPreflightScreenCaptureAccess` | 許可の後もfalseのままだった |
| 起動し直した後 | `CGPreflightScreenCaptureAccess` はtrue。許可は残っていた |
| `NSScreenCaptureUsageDescription` を外した.app | 同じ手順で許可でき、撮影できた |

- 第1フェーズへ持ち込むこと
  - 許可の有無を `CGPreflightScreenCaptureAccess` だけで決めない。許可した直後の同じプロセスでは古い値を返す。SCShareableContentの取得を試し、成功したら撮れる状態とみなす
  - 説明文は撮影に必須ではなかった。設計案のとおり書く
- 署名: 試作.appは `kikigaki-dev` で署名し、bundle IDは本体と分けた。本体の更新をまたいで許可が残るかは、本体に入れてから見る
- macOS 26の定期的な再確認ダイアログ: 試作の期間では観測できない
  - 参考: 同じ方式のUTSUSHIEでは、1度許可した後に再確認を聞かれた記憶はない。タダシの回答(2026-11-09)

## 残り

第0フェーズでは確かめず、第1フェーズへ送るもの。

- 実会議の長さでの枚数: 60分のMTGで何枚になるか。保存の最短間隔としきい値はこれで決める
- 本体の署名と更新をまたいだ許可の維持
- macOS 26の定期的な再確認ダイアログ: 周期がOS任せで観測できない。UTSUSHIEで出た記憶が無いので、出たときの案内だけを用意する
- 比較の基準を保存の成功後に更新すること。「撮る契機の初期値」の節の約束
